## 1. 开头技巧（真实开头例句）

阮一峰几乎从不铺垫背景，开头三种典型套路：**新闻钩子 / 直接抛问题 / 一句定义**。

**（1）用"上周两条大新闻 + 巧合"制造悬念**（《Kimi Code 测评》引言，行 3391–3393）：

> 上周有两条最大的新闻：目前最强的模型 Fable 5 下架，以及 SpaceX 公司上市。
>
> 奇妙的是，这两件事都牵涉到了国产大模型 Kimi。

**（2）直接向读者抛问题，把读者拉进思考**（《MiniMax M3 测评》引言，行 5135–5137）：

> 我问大家一个问题，普通用户的理想大模型应该什么样？
>
> 在我看来，如果你要天天使用一个大模型，它最好同时满足四个条件。

**（3）一句话平实定义，把陌生名词讲清楚再展开**（《周刊#400》"rsync 的争论"，行 3717）：

> rsync 是计算机同步最常用的工具，属于服务器的基本命令。

**（4）时间 + 人物 + 事件，像新闻导语一样交代来龙去脉**（《周刊#399》"中国 AI 大厂访问记"，行 4445）：

> 今年5月上旬，一个美国访问团来到中国，访问了14家 AI 和机器人公司。

**（5）用"上周，某人做了某事"引出话题**（《周刊#398》"Token 费用难以负担"，行 5399）：

> 上周，OpenClaw（龙虾）的创始人彼得·斯坦伯格（Peter Steinberger）贴出了自己的 Token 使用量。

> 提炼：开头 = 一个具体事实/一个具体问题，绝不空泛。第一句往往可独立成段。

## 2. 句式与节奏

**特征 A：长短句交替，观点句独立成段。** 陈述完事实后，用一个极短句子单独成段作转折或强调。（《Kimi Code 测评》，行 3419–3437）

> 我使用下来，最大感受就是，它跟 Claude Code 真的太像了，两者相似度极高。
>
> （……中间叙述命令兼容、权限提示相似……）
>
> 说实话，如果不说，光看 UI 真有可能分不清谁是谁。

**特征 B：口语化的短句收尾，像聊天。**（《Kimi Code 测评》，行 3425）

> 上面第一张图是 Kimi Code 的启动界面，第二张是 Claude Code，是不是很像？

**特征 C：段落极短。** 大量段落只有一到两句，一个意思一段，天然适合手机屏幕阅读。（《周刊#398》，行 5407–5415）

> 根据截图，他一个月发出了760万个请求，消耗的 Token 数量为6030亿。根据预设的费率，这些 Token 价值130万美元！

**特征 D：设问句推进节奏。** 用连续设问把论证一步步往前推。（《MiniMax M3 测评》，行 5147 & 行 5173）

> 那么，有符合这些条件的理想模型吗？

## 3. 论证结构（现象 → 观点 → 论据 → 收尾）

阮一峰的评论段落是稳定的"讲清一件事 + 给出我的判断"结构。完整案例（《周刊#400》"rsync 的争论"，行 3715–3751）：

- **现象**（行 3721）：
> 最近，有人发现，它的 最新版本 3.4.3 是由 Claude 生成的。这引发了轩然大波，怎么可以用 AI 去编写系统的基本命令呢，谁能保证不出错！
- **正反论据**（引用双方，行 3733、3737、3739–3747）：先引批评者的话（"我们非常有理由愤怒……"），再引更难听的比喻，然后完整转述维护者 Andrew Tridgell 的苦衷（年龄精力不足、转向写测试用例）。
- **观点（升华为普遍规律）**（行 3749）：
> 不管这场争论是什么结果，我认为，"AI 写代码 + 人类测试"可能会是将来的大型项目的常见运作模式。
- **收尾（给出现实原因，落地）**（行 3751）：
> 原因很现实，AI 发现的漏洞将会大量涌现，那些没有报酬的开源项目，根本没有人力应对，只能让 AI 去修补代码，工程师转而写测试。

第二个完整案例（《周刊#398》"Token 费用难以负担"，行 5439–5441）——**先算账（论据）→ 下结论（加粗）→ 再延伸到大问题**：

> 总之，AI 编程虽然听起来很美好，但是看到账单的那一刻，公司就会清醒： AI 编程比真人程序员昂贵太多了 。
>
> 所以，AI 会替代程序员吗？对于有大型软件项目的公司，我认为不会大规模替代，因为成本放在那里。

> 提炼：几乎每个话题段落都以"我认为/我猜想/结论就是"收束，把一条科技新闻升级成一个可迁移的普遍判断。

## 9. 文末噪音清单（本段出现的"不需要信息"模式）

以下模式在提炼写作风格时应**剔除**：

1. **每篇文章头部元信息块**（每篇标题下 5 行）：
   - `- 文章 ID: 3286016687-...`
   - `- 公众号 ID: MP_WXS_3286016687`
   - `- 发布时间: 2026-...`
   - `- 原文链接: https://mp.weixin.qq.com/s/...`
   - `- 摘要: ...`（正文引言的重复）
2. **文末 `References` 参考链接列表**：形如 `[1]` / `名称:` / `https://...` 三行一组的长串（如行 3613–3691、4077–4419、4765–5119、5295–5373、5775+）。
3. **周刊固定开场模板**：
   - "这里记录每周值得分享的科技内容，周五发布。"
   - "本杂志 开源 ，欢迎 投稿 。另有 《谁在招人》 服务……合作请 邮件联系 （ yifeng.ruan@gmail.com ）。"
4. **封面图说明**：`封面图` 标题 + 图片链接 + 一句图注（如行 3709–3713"上海体育学院内的绿瓦书店……（ via ）"）。
5. **图片 markdown 链接**：`![图片](https://mmbiz.qpic.cn/...)` 大量堆叠，无文字信息。
6. **周刊纯罗列板块**（仅一句话推荐 + 链接编号，非原创论述）：`科技动态`、`文章`、`工具`、`资源`、`AI 相关`、`图片`、`文摘`（部分文摘含改写故事，需个案判断）、`言论`（引语合集，署名 `-- 出处`）。
7. **`往年回顾` / `往期回顾`**：标题 + `[编号]`（ #35x ）链接列表（如行 4057–4073、4745–4761、5755–5771）。
8. **投稿署名标记**：正文中的 `（ @用户名 投稿）`。
9. **结尾符**：单独成行的 `（完）`。
10. **正文中被换行打断的命令/选项碎片**：如 `/goal`、`/plugins`、`/reload`、`/kimi-datasource [你的问题]` 被单独拆成一行（源自公众号排版），属排版噪音。
11. **赞助/广告插播段**：如 `[活动] XEngineer 大学生实训营`（行 4553–4573）、`Token Plan` 套餐推销段落——虽是本人写作，但属商业插播，风格提炼时应标注区分。

## 附：本段最突出的三个风格特征（供 Skill 提炼）

1. **"讲清一件事 → 我认为 → 升华为普遍规律"的评论闭环**：每段科技新闻都不止于复述，而是以第一人称判断收尾（"我认为""我猜想""结论就是"），并把具体事件抽象成一条可迁移的规律。
2. **短段落 + 数字/换算 + 加粗结论**的强节奏排版：一个意思一段，用具体数字和"换算成人民币/每天多少钱"制造冲击，把最想让人记住的判断整句加粗。
3. **极致口语化与读者对话**："大家猜猜看""是不是很像""说实话""老读者知道"，把技术内容写得像面对面聊天，配合生活化类比（咖啡杯型、手机发布会）降低理解门槛。
